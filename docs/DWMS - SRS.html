1. Introduction

1.1 Purpose

This Software Requirements Specification (SRS) establishes the complete functional, structural, external API, and performance scope of the Multi-Tenant B2B Warehouse Management System (WMS). It serves as the single source of truth for full-stack software engineers, QA automation professionals, database administrators, and solution architects.

1.2 Scope of the System

The system provides operational automation for product distributors (Dealers) who purchase goods directly from manufacturers, manage physical stock across one or more warehouses, and fulfill wholesale sales orders sent to retail shops. Key functionality includes:

  • Multi-tenant architecture isolating dealer corporate accounts, users, and business data.
  • Inbound Procurement lifecycle (Purchase Orders $\rightarrow$ Goods Receipt Notes $\rightarrow$ Backorders).
  • Real-time multi-warehouse inventory allocation (`quantity_on_hand` vs `quantity_allocated`).
  • Outbound Sales Fulfillment (Sales Orders $\rightarrow$ Pick & Pack $\rightarrow$ Dispatch $\rightarrow$ Shop Balance settlement).
  • Strict audit logging through an append-only stock movement transaction ledger.

2. Overall System Description & Roles

2.1 User Roles and Permissions (RBAC Matrix)

Role Tenant Scope Permissions & Capabilities
Super Admin Platform Global Onboards new Dealers, views platform diagnostics, overrides system flags. Cannot access private stock financial metrics unless explicitly invited.
Dealer Admin / Owner Tenant (`dealer_id`) Full CRUD over tenant users, company settings, financial dashboards, credit limits, suppliers, shops, and warehouses.

2.2 Workflow Overview

The operational flow spans three primary cycles:

  1. Inbound Cycle: Purchase Order issued to Manufacturer $\rightarrow$ Goods received at warehouse loading dock $\rightarrow$ GRN created $\rightarrow$ Stock ledger incremented (`PO_RECEIPT`).
  2. Inventory Control Cycle: Stock sits in warehouse bin locations $\rightarrow$ Re-order limit monitors $\rightarrow$ Intra-warehouse transfers or manual adjustments recorded (`ADJUSTMENT`).
  3. Outbound Cycle: Sales Order created for Shop $\rightarrow$ Credit Limit & Available Stock checked $\rightarrow$ Order Approved (`quantity_allocated` locked) $\rightarrow$ Pick & Pack list generated $\rightarrow$ Order Dispatched $\rightarrow$ Delivered $\rightarrow$ `quantity_on_hand` and `quantity_allocated` decremented, Shop balance credited.

3. Functional Requirements (Detailed Modules)

SRS-MOD-01: Multi-Tenant Identity & Access Management (IAM) MUST HAVE

Description: Provisions isolated tenant accounts and enforces stateless authentication.

  • SRS-IAM-001 (Atomic Registration): System shall accept dealer onboarding data and execute a single database transaction creating the `dealers` record, an `ADMIN` user in `users`, and a default `warehouses` record ("Main Warehouse"). Failure at any step must trigger a full rollback.
  • SRS-IAM-002 (JWT Context Injection): Upon authentication via `POST /auth/login`, system shall issue a signed JWT payload containing `userId`, `dealerId`, and `role`.
  • SRS-IAM-003 (Tenant Isolation Guard): NestJS execution pipeline must intercept every incoming HTTP request, parse `dealerId` from the verified JWT, and inject it into database filters. Unowned data access must return HTTP 404 (Not Found) to prevent resource scanning.

SRS-MOD-02: CRM & Entity Directory MUST HAVE

Description: Manages upstream suppliers (Manufacturers) and downstream customers (Shops).

  • SRS-CRM-001 (Manufacturer Profiles): System shall allow managers to manage profiles for manufacturers including `lead_time_days`, contact information, and address.
  • SRS-CRM-002 (Shop Profiles & Addresses): System shall store retail shop clients with distinct `shipping_address` and `billing_address` fields.
  • SRS-CRM-003 (Credit Limit Enforcement): System shall track `credit_limit` and `current_balance` per shop. If `(current_balance + order_total) > credit_limit`, system must automatically reject Sales Order approval unless overridden by a `Dealer Admin`.

SRS-MOD-03: Product Catalog & Inventory Ledger MUST HAVE

Description: Tracks stock counts, physical locations, and movements.

  • SRS-INV-001 (Product Catalog & SKUs): System shall maintain products with unique SKU codes per tenant, barcodes, `cost_price`, and `selling_price`.
  • SRS-INV-002 (Real-Time Stock Equations): System must track stock using the formula:
    Available Stock = quantity_on_hand - quantity_allocated
  • SRS-INV-003 (Append-Only Movement Ledger): Direct manual modification of inventory quantities without an entry in `stock_movements` table is strictly impossible at the DB schema level. Every change must log `user_id`, `movement_type`, and quantity delta (+/-).
  • SRS-INV-004 (Concurrency Safety): During order allocation, system must execute `SELECT ... FOR UPDATE` row locks on affected `inventory` rows to prevent race conditions during simultaneous sales order processing.

SRS-MOD-04: Inbound Procurement (Procure-to-Pay) MUST HAVE

Description: Handles purchasing goods from manufacturers and receiving them into warehouses.

  • SRS-PRO-001 (Purchase Order Lifecycle): System shall enforce valid PO state transitions: `DRAFT` $\rightarrow$ `ORDERED` $\rightarrow$ `PARTIALLY_RECEIVED` $\rightarrow$ `COMPLETED` / `CANCELLED`.
  • SRS-PRO-002 (Goods Receipt Note): When trucks arrive, warehouse staff shall input received counts against open PO line items.
  • SRS-PRO-003 (Stock Intake Integration): Confirming a GRN must automatically:
    1. Increment `inventory.quantity_on_hand` by received amount.
    2. Write a `PO_RECEIPT` entry into `stock_movements`.
    3. Calculate remaining items on backorder if received count < ordered count.

SRS-MOD-05: Outbound Fulfillment (Order-to-Cash) MUST HAVE

Description: Processes shop purchase requests, stock picking, and shipping.

  • SRS-FUL-001 (Sales Order Creation & Allocation): Approving an SO locks stock by increasing `quantity_allocated` on the target warehouse inventory record. Physical `quantity_on_hand` remains unchanged.
  • SRS-FUL-002 (Pick List Generation): System shall generate actionable Picking Lists sorted by warehouse bin locations to minimize staff walking distance.
  • SRS-FUL-003 (Dispatch & Ledger Settlement): Transitioning an SO state to `DELIVERED` must execute an atomic transaction:
    1. Decrement `quantity_on_hand` by shipped quantity.
    2. Decrement `quantity_allocated` by shipped quantity.
    3. Increase shop's `current_balance` by invoice total.
    4. Write `SO_DISPATCH` record to `stock_movements`.

5. Non-Functional Requirements (NFR)

5.1 Security Requirements

  • NFR-SEC-01 (Password Encryption): All passwords stored in database must be hashed using `Argon2id` with a minimum memory cost of 65536 KB and time cost of 3 iterations.
  • NFR-SEC-02 (Data Isolation): System shall enforce complete multi-tenant separation. Under no condition may a database query execute without `where: { dealerId }` criteria attached, verified via automated static analysis and backend NestJS interceptors.
  • NFR-SEC-03 (Token Lifetime): Access JWTs shall expire after 15 minutes. Refresh tokens must be stored in HTTP-only, SameSite=Strict cookies with a maximum life of 7 days.

5.2 Performance & Concurrency Requirements

  • NFR-PER-01 (API Response Latencies): 95% of standard read requests (catalog lookup, stock check) must respond in under 150ms under normal load.
  • NFR-PER-02 (Concurrent Order Processing): System shall handle up to 50 concurrent sales order allocations per second per dealer without deadlocks or stock over-commitments (enforced via DB row locks).

5.3 Data Integrity & Precision

  • NFR-DAT-01 (Monetary Precision): All currency fields (`cost_price`, `selling_price`, `credit_limit`, `current_balance`) must use fixed-point `NUMERIC(12,2)` columns to eliminate floating-point arithmetic rounding errors.
  • NFR-DAT-02 (Negative Quantity Protection): Database tables for `inventory` must include strict check constraints:
    CHECK (quantity_on_hand >= 0) AND CHECK (quantity_allocated >= 0)
