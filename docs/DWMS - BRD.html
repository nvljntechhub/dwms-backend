Multi-Tenant B2B Warehouse Management System (WMS)

Target Audience Wholesale Distributors & Dealers

Document Version 1.0.0

1. Executive Summary & Business Scope

1.1 Project Overview

The Multi-Tenant B2B Warehouse Management System (WMS) is a cloud-based web application designed specifically for product distributors and wholesale dealers. The system manages the end-to-end operational lifecycle: acquiring goods directly from manufacturers, managing stock across physical warehouses, and selling/delivering items to retail shops.

1.2 Core Business Goals

  • Multi-Tenant Isolation: Enable independent wholesale dealers to operate securely on a shared infrastructure without data exposure risks.
  • Inventory Accuracy: Eliminate stock discrepancies using an append-only audit ledger (stock_movements) and real-time reservation logic.
  • Financial Risk Mitigation: Enforce automated credit limit checks before approving outbound sales orders to retail shops.
  • Operational Traceability: Track full chain of custody for goods from purchase order (PO) receipt to final delivery proof at retail locations.

1.3 Out of Scope

  • Direct-to-Consumer (D2C) e-commerce storefronts.
  • Point of Sale (POS) register operations for retail shop counters.
  • Integrated manufacturing line management.

2. User Roles & Access Control (RBAC)

The system supports five distinct user types across two operational levels:

System Level

  • Platform Super Admin: Onboards dealers, monitors tenant metrics, manages platform billing, and maintains global configurations.

Dealer Level (Tenant-Scoped)

  • Dealer Admin / Owner: Full access to company setup, staff creation, financial reporting, and warehouse configuration.
  • Warehouse Manager: Approves Purchase Orders and Sales Orders, manages stock adjustments, overrides inventory counts, and creates product records.
  • Warehouse Staff: Performs stock receiving (GRN), executes pick/pack workflows, logs stock movements, and views inventory counts.
  • Delivery Driver: Views assigned delivery routes, marks order dispatch/delivery states, and captures proof of delivery (POD).

3. Functional Requirements (FR)

FR-1: Multi-Tenancy & Dealer Onboarding

  • FR-1.1 Automated Tenant Onboarding: The system must execute an atomic database transaction during registration that inserts:
    1. A new record in dealers.
    2. The initial users account with ADMIN privileges.
    3. A default warehouses record ("Main Warehouse").
  • FR-1.2 Data Isolation: Every query across tenant-scoped tables must enforce filtering by dealer_id extracted from the validated JWT token.

FR-2: Contact Directory (CRM)

  • FR-2.1 Manufacturer Management: Managers must be able to record manufacturer details including lead times (in days), contact persons, tax IDs, and return addresses.
  • FR-2.2 Shop Management: Managers must be able to manage retail shop profiles, including distinct shipping and billing addresses, primary contact details, approved credit limits, and active balance tracking.
  • FR-2.3 Credit Restriction: The system must block order approval if an order's value causes a shop's current_balance to exceed its credit_limit.

FR-3: Product Catalog & Pricing

  • FR-3.1 SKU Management: Products must be indexed by a unique Stock Keeping Unit (SKU) per dealer, with scannable barcode fields (EAN/UPC), category IDs, and supplier cross-references.
  • FR-3.2 Two-Tier Pricing: Each product must store a cost_price (purchase cost from manufacturer) and a selling_price (wholesale cost billed to shops).
  • FR-3.3 Low Stock Thresholds: Products must support a configurable reorder_level triggering automated alerts when available stock drops below the threshold.

FR-4: Warehouse & Real-time Inventory Management

  • FR-4.1 Multi-Warehouse Support: Dealers must be able to define multiple physical facilities with unique codes (e.g., WH-01).
  • FR-4.2 Real-time Stock Metrics: Inventory must track three distinct values per product/warehouse pair:
    • quantity_on_hand: Physical count inside the building.
    • quantity_allocated: Locked stock reserved for approved Sales Orders.
    • Available Quantity: Dynamically calculated as quantity_on_hand - quantity_allocated.
  • FR-4.3 Append-Only Audit Ledger: Direct mutation of stock counts without an accompanying stock_movements log entry is strictly prohibited. Movement types include PO_RECEIPT, SO_DISPATCH, ADJUSTMENT, TRANSFER_IN, and TRANSFER_OUT.

FR-5: Inbound Procurement (Manufacturer → Warehouse)

  • FR-5.1 Purchase Order Lifecycle: Support status state transitions: DRAFT → ORDERED → PARTIALLY_RECEIVED → COMPLETED / CANCELLED.
  • FR-5.2 Goods Receipt Note (GRN): Warehouse staff must log received quantities against open PO line items.
  • FR-5.3 Partial Deliveries & Backorders: Receiving partial shipments must update quantity_on_hand, adjust item counts received, and leave remaining quantities on open backorder status.

FR-6: Outbound Fulfillment (Warehouse → Shop)

  • FR-6.1 Sales Order Lifecycle: Support status state transitions: PENDING → APPROVED → PICKING → SHIPPED → DELIVERED / CANCELLED.
  • FR-6.2 Stock Allocation Lock: Approving a Sales Order must increment quantity_allocated without decreasing quantity_on_hand until physical dispatch.
  • FR-6.3 Pick & Pack Generation: The system must generate consolidated Pick Lists grouped by warehouse bin locations.
  • FR-6.4 Dispatch & Settlement: Marking an order as DELIVERED must decrement quantity_on_hand and quantity_allocated, increase the shop's current_balance, and record a SO_DISPATCH stock movement.

4. Non-Functional Requirements (NFR)

NFR-1: Security & Compliance

  • Authentication: Stateless authentication via JWT signed using HS256/RS256 with 15-minute expiration and HTTP-only refresh tokens.
  • Authorization: Role-Based Access Control (RBAC) enforced via server-side guards on every API endpoint.
  • Tenant Protection: Zero tolerance for Insecure Direct Object Reference (IDOR) vulnerabilities; requests querying unowned dealer_id parameters must yield a 404 Not Found response.

NFR-2: Performance & Data Integrity

  • Concurrency Handling: Stock reservation workflows must use explicit row-level database locking (SELECT ... FOR UPDATE) or atomic database transactions to eliminate race conditions during simultaneous orders.
  • API Latency: Read queries for stock levels and order dashboards must return within 200ms at p95 under standard load.

NFR-3: Reliability & Auditability

  • Financial Integrity: All price and monetary fields must use NUMERIC(12,2) precision to prevent floating-point rounding errors.
  • Data Immutability: Historical stock movements and ledger transactions must be read-only and preserved for financial and operational auditing.
